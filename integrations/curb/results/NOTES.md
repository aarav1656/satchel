Working notes, 2026-10-02.

- Finding that changed the plan: satchel-sdk 0.1.0 cannot produce Curb's role keys. The public API (src/index.ts, dist/index.d.ts, package exports map has only ".") exposes seal/unseal (AES-GCM, random IV per call), fingerprint (8 hex chars, documented as safe to show), grant/revoke (needs a funded registry owner and a transaction) and registryOwner (one address, key not exported). HKDF namespace keys, per-epoch data keys and the registry owner key are computed inside the session and never leave it. Nothing returns secp256k1 key bytes, and no deterministic function of the passkey can be read out per role. Hand-rolling one from fingerprint(ns) would turn a value the SDK says is safe to show into a signing key, so it was not done.
- Consequence for the brief: "derive both role keys with the satchel SDK" is not possible with 0.1.0. The patch therefore adds no satchel dependency and there is no local-proof/ commit (nothing to resolve from a tarball). What an SDK change would have to offer: a session method that returns a namespaced secp256k1 signer (for example `session.signer(ns("curb/owner"))`), with the key zeroed on close(). With that, Curb could move to satchel namespaces; it would still need the old derivation kept for existing accounts, because satchel's root is the PRF of Mera's default salt and Curb's accounts come from PRF of sha256("curb.owner.v1") and sha256("curb.trade.v1"). Different PRF salts give unrelated outputs, so satchel-derived keys can never equal Curb's current keys.
- What was built instead, same user outcome: WebAuthn's PRF extension evaluates two salts per ceremony (eval.first, eval.second). Curb's two role salts now ride in one ceremony for createAccount and signIn, through a small WebAuthnClient handed to Mera's own createPasskeyWithPrfOutput/getPasskeyPrfOutput (mirrors Mera's browserWebAuthnClient, adds the second salt, captures the second output). The keys do not change, so no migration and no version flag are needed. Measured: main's signIn on a passkey the patch made returns the same two addresses, and the patch's signIn on a passkey main made returns main's addresses.
- Fallback: if the authenticator returns no second output, the old second prompt runs (derive()). Never worse than main, never a different key. Mutant control (second output discarded) shows 2 prompts and identical addresses.
- Untouched on purpose: withOwnerKey and openTradingSession keep one single-salt prompt each, so the long-lived trading session still never derives the owner key (D-012, BRIEF section 10). Both role PRFs exist in memory together only inside createAccount/signIn, as they did on main.
- docs/DECISIONS.md line 145 ("Creating an account costs two biometric prompts; signing in costs two") becomes untrue after this patch. Not changed: the patch is one file by instruction. Listed in PR.md for the Curb team.
- Harness: bundles the real keys.ts with bun (three bundles: patched, mutant, unpatched), page outside their src, node_modules symlinked to /tmp/curb/web/node_modules, run through ~/.claude/scratch/cdp-tab.mjs with VAUTH=1, tclick, PIN_FILE ~/.cache/qa-tab-satchel-curb, profile deepsurge. Each run gets a fresh virtual authenticator, so runs 1 to 4 are four different passkeys. Prompt count is the number of navigator.credentials.create plus get calls. No transaction is sent anywhere; the page prints addresses only.
- Plumbing notes: `bhn deepsurge status` timed out once inside cdp-tab.mjs (8 s limit, shared browser busy), so run.sh resolves the CDP port first with retries and passes CDP_PORT. bun build prints "Internal error: directory mismatch ... tsconfig.build.json" on every build; the bundles are produced and used, the message is bun's own and harmless here.

- Blind spots: the authenticator is Chrome's virtual platform authenticator, not iCloud Keychain, Google Password Manager, 1Password or a hardware key, so whether those return the second PRF output at creation and at assertion is unmeasured (the fallback covers a "no" with the old two prompts). The page is a harness, not Curb's onboarding screen, and Curb's own browser e2e suite was not run. Nothing was sent on chain. The onboarding step indicator now moves from one role to the other with no prompt in between; it was not looked at in a browser.
